1. System Calls, Processes & Threads

What the OS actually is, how programs ask it for help, and the difference between a process and a thread.

What is an OS? 🔵 High-Yield · orientation

Think of the OS as the manager of a shared house: the hardware (CPU, RAM, disk) is the house, programs are the tenants, and the OS decides who gets the kitchen (CPU) and when, keeps tenants out of each other's rooms (memory protection), and gives everyone simple keys instead of raw wiring (abstraction: files instead of disk sectors).

User mode
Normal programs run here. Cannot touch hardware or other programs' memory directly.
Kernel mode
The OS core runs here with full power. A mode bit in the CPU tracks which mode you are in.

System calls 🟢 Core

A system call is how a user program politely asks the kernel to do something privileged (open a file, create a process, allocate memory). It works via a trap: a special instruction that flips the CPU into kernel mode and jumps to a fixed kernel routine.

Common ones: fork (create process), exec (replace process image), wait, exit, open/read/write/close.

GATE trap
Privileged instructions (I/O, halt, changing the mode bit, memory-management registers) work only in kernel mode. Trying them in user mode raises a trap. Also: a trap/system call is a software (synchronous) event, an interrupt is a hardware (asynchronous) event.

Process = a program in execution 🟢 Core

A program is a file sitting on disk. A process is that program running: it has its own address space with text (code), data (globals), heap (malloc) and stack (function calls), plus a record the OS keeps about it called the PCB (Process Control Block): PID, state, program counter, CPU registers, memory info, open files, scheduling info.

Process state diagram

Context switch

When the CPU moves from process A to B, the OS saves A's registers/PC into A's PCB and loads B's. It's pure overhead (no user work happens), so the OS wants it cheap and rare.

fork() — the favourite GATE question 🟢 Core

fork() clones the calling process. Both continue from the next line. It returns 0 in the child, the child's PID in the parent, and −1 on failure. Each fork doubles the number of processes.

Worked numerical
Q: How many processes exist (including the original) after fork(); fork(); fork(); and how many times is printf("hi") printed if it comes after all three?
A: 1 → 2 → 4 → 8 processes, so total = 2ⁿ = 2³ = 8 (7 children). Every process runs the printf → 8 times.
Worked numerical
Q: How many child processes are created by if (fork() == 0) fork(); ?
A: Parent forks child C1 (in C1, fork returned 0). Only C1 enters the if-body and forks C2. The parent skips it. Total = 3 processes → 2 children (C1, C2). Rule: a fork inside a condition only doubles the processes that satisfy the condition.
Worked numerical
Q: for (i = 0; i < 4; i++) fork(); — how many processes in total?
A: Every process (including new ones) executes every remaining iteration, so it doubles each round: 2⁴ = 16 total, 15 newly created.

Threads 🟢 Core

A thread is a lightweight unit of execution inside a process. Threads of one process share code, data, heap, open files; each has its own stack, registers and PC. Creating a thread and switching between threads is much cheaper than for processes.

Threads share the heap and globals, so they need synchronization (Part 2). Each thread keeps its own stack and register set, that is why local variables are not shared.

Zombie and orphan processes 🔵 High-Yield · frequent MCQ

Zombie (defunct)
The process has terminated, but its process-table entry (PID and exit status) stays because the parent has not yet called wait(). It uses no CPU or memory, only a table slot. Removed when the parent calls wait(), or when the parent dies and init reaps it.
Orphan
The process is still running but its parent has terminated first. It is adopted by init (PID 1, or systemd), which later calls wait() for it, so orphans never become permanent zombies.
GATE trap
Zombie = dead but not reaped. Orphan = alive but parentless. You cannot "kill" a zombie — it is already dead; the fix is to make its parent reap it.

Copy-on-write (COW) fork 🔵 High-Yield · fork() follow-up

A naive fork() copies the whole address space, which is wasted if the child calls exec() immediately. With COW the child initially shares the parent's physical frames, all marked read-only. The first write to a shared page raises a protection fault; the OS then copies only that page and makes the copy private and writable. Pages that are never written are never copied.
Worked numerical
Q: A parent with 100 pages forks a child. The child writes to 10 pages and the parent writes to none. How many extra frames are used, with and without COW?
A: Without COW: 100 extra frames (full copy). With COW: only the 10 written pages are copied → 10 extra frames, and the other 90 stay shared.

Context-switch overhead 🔵 High-Yield · numerical variant

Worked numerical
Q: Round Robin with quantum q = 10 ms and context-switch time s = 2 ms. What fraction of time is useful work (assume every quantum is fully used)?
A: Each cycle = q + s = 12 ms, of which 10 ms is useful → efficiency = 10/12 = 83.3% (overhead 16.7%). General: efficiency = q / (q + s).
Quick Facts for Exam
• Among non-preemptive algorithms, SJF gives the minimum average waiting time; SRTF is optimal among preemptive ones.
• FCFS has the convoy effect; RR gives the best (lowest) response time for interactive systems.
• I/O-bound processes use short CPU bursts; CPU-bound use long bursts. Good schedulers favour I/O-bound ones to keep devices busy.
• If all processes arrive at t=0, FCFS and non-preemptive SJF need no arrival-time juggling, just sort by order/burst.

Highest Response Ratio Next (HRRN) 🔵 High-Yield · occasional PYQ

MLFQ rules: a new job enters the top queue (highest priority, smallest quantum). If it uses its whole quantum it is demoted one level (it looks CPU-bound); if it blocks for I/O before the quantum ends it stays high (it looks interactive). So MLFQ favours short and I/O-bound jobs without knowing burst lengths in advance — it approximates SRTF. Design parameters: number of queues, algorithm per queue, promotion rule, demotion rule, and the queue a new job enters.

3. Synchronization & IPC

What goes wrong when processes share data, and the tools that fix it: atomic hardware instructions, semaphores, mutexes and monitors — plus priority inversion and the deadlock / livelock / starvation distinction.

Race condition & the critical section 🟢 Core

If two threads update shared data at the same time, the final answer depends on who wins the race. Even x = x + 1 is really three steps: load x → add 1 → store x, and a context switch can land between them. The code touching shared data is the critical section (CS).

A correct solution needs all three:
1. Mutual exclusion: only one process in the CS at a time.
2. Progress: if the CS is free, one of the waiting processes must be allowed in (no needless blocking by processes outside the CS).
3. Bounded waiting: a limit on how many times others can enter before a waiting process gets its turn (no starvation).

Peterson's solution (2 processes, pure software) 🟢 Core

// shared: flag[2] = {false,false};  int turn;
// process i (j = 1-i):
flag[i] = true;          // I want to enter
turn = j;                // but you go first if you also want
while (flag[j] && turn == j);   // busy wait
   /* critical section */
flag[i] = false;         // exit

It satisfies mutual exclusion, progress and bounded waiting. Real hardware uses atomic instructions like test-and-set / compare-and-swap instead. Note: a plain lock variable (while(lock); lock=1;) does not work, because checking and setting are two separate steps.

Semaphores 🟢 Core

A semaphore is an integer S touched only by two atomic operations:

wait(S)   /* P */ :  S--;  if (S < 0) block this process
signal(S) /* V */ :  S++;  if (S <= 0) wake up one blocked process
Binary semaphore / mutex
Value 0 or 1. Used for mutual exclusion: init to 1, wait before the CS, signal after.
Counting semaphore
Counts available units of a resource (e.g. 5 printers, or free buffer slots).
Worked numerical
Q: A counting semaphore starts at S = 3. After 5 wait() and 1 signal() operations, what is S and how many processes are blocked?
A: S = 3 − 5 + 1 = −1. A negative value means |S| processes are blocked → 1 process blocked. (Rule: S ≥ 0 ⇒ S free units; S < 0 ⇒ |S| waiting processes.)
Worked numerical
Q: Semaphore S = 10 initially. 6 wait() and 4 signal() operations complete. What is S?
A: 10 − 6 + 4 = 8 (nobody blocked, since S never went below 0).

Classic problems 🟢 Core

1. Producer–Consumer (bounded buffer of N slots)

semaphore mutex = 1, empty = N, full = 0;

Producer:                Consumer:
 wait(empty);             wait(full);
 wait(mutex);             wait(mutex);
   add item                 remove item
 signal(mutex);           signal(mutex);
 signal(full);            signal(empty);

empty counts free slots, full counts filled slots, mutex guards the buffer.

GATE trap
Swap the order to wait(mutex); wait(empty); in the producer and you get a deadlock: a producer holding the mutex sleeps on a full buffer, and the consumer can never take the mutex to free a slot. The order of waits matters, the order of signals does not.

2. Readers–Writers

Many readers may read together, but a writer needs exclusive access. The simple solution favours readers (writers can starve); a writer-priority version flips this. Uses a read_count protected by a mutex, and a wrt semaphore for writers.

3. Dining Philosophers

5 philosophers, 5 forks, each needs both neighbouring forks. If everyone grabs their left fork at the same time, all wait forever → deadlock. Fixes: allow at most 4 to sit; pick up both forks atomically; or make one philosopher pick right-first (breaks circular wait).

GATE classic: lost updates
Q: Two threads each run for (i=0;i<N;i++) x = x + 1; on a shared x = 0, with no synchronization and non-atomic load/add/store. What are the maximum and minimum possible final values of x (N ≥ 2)?
A: Max = 2N (no interleaving damage). Min = 2:
1. T1 loads x = 0, then is paused.
2. T2 runs N−1 full iterations → x = N−1.
3. T1 stores 1. T2 loads 1 for its last iteration and is paused.
4. T1 runs its remaining N−1 iterations → x = N.
5. T2 stores 1+1 = 2. Final x = 2.

Hardware support: test-and-set, swap and compare-and-swap 🟢 Core

Pure-software locks (Peterson) are rarely used on real machines. The CPU instead gives atomic read-modify-write instructions that cannot be interrupted halfway:

boolean TestAndSet(boolean *lock) {      // executes atomically
    boolean old = *lock;  *lock = true;  return old;
}
// shared: boolean lock = false;
do {
    while (TestAndSet(&lock)) ;        // spin until old value was false
        /* critical section */
    lock = false;
} while (true);

int CompareAndSwap(int *v, int expected, int new_value) {   // atomic
    int tmp = *v;
    if (tmp == expected) *v = new_value;
    return tmp;
}
PropertySimple test-and-set lock
Mutual exclusionYes — only the process that saw false enters
ProgressYes
Bounded waitingNo — a fast process can release and re-grab the lock every time, so another one can spin forever (starvation). A bounded-waiting version adds a waiting[n] array and hands the lock to the next waiting process in cyclic order
CostBusy waiting: the CPU burns cycles while spinning
Spinlock = a lock built on busy waiting. It wastes CPU on a single core (the lock holder cannot run while you spin), but on a multiprocessor it beats blocking when the critical section is shorter than a context switch. A blocking mutex/semaphore instead puts the waiter to sleep and wakes it on release. Rule of thumb: short CS on many CPUs → spinlock; long CS → sleep.
GATE trap
Disabling interrupts also gives mutual exclusion, but only on a single processor and only for kernel code — on a multiprocessor the other CPUs keep running, so it does not work. And a plain while(lock); lock=1; fails because checking and setting are two separate steps; test-and-set fuses them into one atomic step.

Monitors & condition variables 🔵 High-Yield · concurrency background

A monitor is a language-level construct: shared data plus the procedures that touch it, packaged so that only one process can be active inside the monitor at a time. The compiler/runtime supplies the mutual exclusion, so the programmer cannot forget a wait(mutex). To wait for a condition (e.g. "buffer not empty") the monitor uses condition variables with two operations:

x.wait()    // the caller releases the monitor lock and blocks on x
x.signal()  // wake ONE process waiting on x; if none is waiting, it does NOTHING

monitor BoundedBuffer {
    int count = 0;  condition notFull, notEmpty;
    void put(item) {
        while (count == N) notFull.wait();   // while, not if (Mesa-safe)
        add item; count++;
        notEmpty.signal();
    }
    item get() {
        while (count == 0) notEmpty.wait();
        remove item; count--;
        notFull.signal();
        return item;
    }
}

signal(S) is remembered (S is incremented even if nobody waits)x.signal() is lost if no process is waiting on x
wait(S) blocks only if S would go negativex.wait() always blocks
Programmer must pair every wait/signal correctlyMutual exclusion is automatic; only the condition logic is manual
Signal semantics. When P calls x.signal() and Q is waiting on x, both cannot run inside the monitor at once. Hoare (signal-and-wait): P hands the monitor to Q immediately and waits, so Q knows the condition is still true — an if test is enough. Mesa (signal-and-continue): P keeps running and Q only becomes ready; the condition may have changed before Q gets in, so Q must re-check in a while loop. Most real systems (Java, pthreads) use Mesa semantics, so always write while (cond) x.wait();.

Priority inversion & priority inheritance 🔵 High-Yield · concurrency background

Priority inversion happens when a high-priority task is stuck waiting for a lock held by a low-priority task, and a medium-priority task that does not need the lock keeps preempting the low one — so the high-priority task is effectively delayed by the medium one.

L (low) takes lock → H (high) arrives, blocks on the lock
→ M (medium) arrives and preempts L (M has higher priority than L)
→ L cannot run, so it cannot release the lock → H waits as long as M runs
Fix — priority inheritance: while L holds a lock that H wants, L temporarily inherits H's priority. M can no longer preempt L, L finishes its critical section quickly, releases the lock, drops back to low priority, and H runs. (The 1997 Mars Pathfinder resets are the textbook real-world example.) A related fix is the priority ceiling protocol: a lock's ceiling is the highest priority of any task that may use it, and a task holding it runs at that ceiling.
Worked example
Q: Priorities H > M > L. L starts at t=0 and locks R; it needs 4 ms of CPU inside the lock in total. H arrives at t=2 and requests R (it blocks). M arrives at t=3 and needs 10 ms of CPU. When does H get R (a) without and (b) with priority inheritance?
A: By t=2 L has used 2 ms in the lock. (a) Without inheritance: L runs t=2→3 (1 ms more, 1 ms left). At t=3 M preempts L, since M outranks L, and runs t=3→13. L finishes its last 1 ms at t=13→14, so H gets R at t=14 — held up by M's entire burst although H outranks M.
(b) With inheritance: from t=2 L runs at H's priority, so M cannot preempt it. L runs t=2→4, releases R, and H gets R at t=4.

4. Deadlocks

Everyone is waiting for someone else, forever. Learn the four conditions, the graph test, and Banker's algorithm (a GATE favourite).

The four necessary conditions (Coffman) 🟢 Core

A deadlock can occur only if all four hold at once:

ConditionMeaningBreak it by
Mutual exclusionA resource is held by one process at a timeMake resources sharable (rarely possible)
Hold and waitHolds some resources while waiting for moreRequest everything at once
No preemptionResources cannot be forcibly taken awayAllow the OS to preempt
Circular waitP1 waits for P2 waits for ... waits for P1Number resources, request in increasing order

Resource Allocation Graph (RAG) 🟢 Core

Edge R → P = allocated, P → R = requested. Here P1 holds R1 and wants R2, while P2 holds R2 and wants R1: a cycle.

GATE rule
• Every resource has a single instance: cycle ⇔ deadlock.
• Resources have multiple instances: cycle is necessary but not sufficient. Check whether a free instance or a process outside the cycle can still finish.
• No cycle ⇒ no deadlock.

Handling deadlocks 🟢 Core

Prevention
Design so at least one Coffman condition can never hold.
Avoidance
Grant a request only if the system stays in a safe state (Banker's algorithm).
Detection & recovery
Let deadlock happen, detect via graph/algorithm, then kill processes or preempt resources.
Ignore (ostrich)
What Linux/Windows mostly do: deadlocks are rare, so avoid the overhead.

Safe state = there exists an order (safe sequence) in which every process can finish. Safe ⇒ no deadlock; unsafe ⇒ deadlock possible (not certain).

Banker's algorithm 🟢 Core

Keep Need = Max − Allocation. Repeatedly pick any process whose Need ≤ Available, let it finish, and add its Allocation back to Available. If all can finish, the state is safe.

Minimum resources for deadlock freedom 🟢 Core

n processes, each needs at most m units of one resource type.
Deadlock-free if   R ≥ n(m − 1) + 1
Logic: worst case each process holds m−1 units and all wait for one more. One extra unit lets someone finish.
Worked numerical
Q: 3 processes each need up to 4 units of the same resource. Minimum units to guarantee no deadlock?
A: R = 3(4−1) + 1 = 10. With 9 units, each could hold 3 and all be stuck.
Worked numerical
Q: 12 units of a resource, each process needs at most 3. Maximum number of processes that keeps the system deadlock-free?
A: Need 12 ≥ n(3−1)+1 = 2n+1 → n ≤ 5.5 → 5 processes.

Wait-for graph 🔵 High-Yield · deadlock detection

When every resource has a single instance, the resource-allocation graph can be collapsed into a wait-for graph: delete the resource nodes and draw Pi → Pj whenever Pi is waiting for a resource currently held by Pj. A cycle in the wait-for graph ⇔ deadlock. With multiple instances per resource, a cycle in the RAG is only necessary — use the detection algorithm instead (see Q12). The OS runs cycle detection periodically, or when CPU utilisation drops; a cycle search on n processes costs O(n²). (DBMS uses the same idea for transactions.)
Worked example
Q: P1 holds R1 and requests R2; P2 holds R2 and requests R1; P3 holds R3 and requests R1. Is there a deadlock?
A: Wait-for edges: P1 → P2 (R2 is held by P2), P2 → P1 (R1 is held by P1), P3 → P1 (R1 is held by P1). 
P1 ⇄ P2   is a cycle → P1 and P2 are deadlocked.
P3 → P1   is only an edge INTO the cycle: P3 is blocked behind the deadlock but is not on a cycle.

5. Memory Management & Paging

How the OS shares RAM between processes, keeps them apart, and why paging beats old-style partitions.

Logical vs physical addresses 🟢 Core

A program uses logical (virtual) addresses, as if it owns memory starting at 0. The hardware MMU translates them into physical addresses in real RAM. This gives protection (you cannot reach another process's memory) and lets the OS place programs anywhere.

Contiguous allocation & fragmentation 🟢 Core

Internal fragmentation
Wasted space inside an allocated block (fixed partitions, or the last page of a process).
External fragmentation
Enough total free memory, but split into holes too small to use. Fixed by compaction or by paging.

Worst fitLargest hole (leaves a big leftover)
Worked numerical
Q: Free holes (in order): 100K, 500K, 200K, 300K, 600K. Processes arrive: 212K, 417K, 112K, 426K. Place them with First, Best and Worst fit.
A: 
First fit: 212→500 (rem 288) | 417→600 (rem 183) | 112→288 (rem 176) | 426 → NO hole ≥ 426 → waits

Worst fit: 212→600 (rem 388) | 417→500 (rem 83)  | 112→388 (rem 276) | 426 → NO hole → waits
Best fit is the only one that places all four here. No algorithm always wins.

Paging 🟢 Core

Split logical memory into fixed-size pages and physical memory into same-size frames. Any page can go into any free frame, so there is no external fragmentation (only a bit of internal fragmentation in the last page). A page table maps page number → frame number.

Logical address = [ page no | offset ]
→
Page table[page no] = frame no
→
Physical address = [ frame no | offset ]
offset bits      = log2(page size)
page-number bits = logical address bits − offset bits
frame-number bits= physical address bits − offset bits
page table size  = (number of pages) × (PTE size)
Worked numerical
Q: 32-bit logical address, 4 KB pages, 1 GB physical memory, 4-byte page table entry. Find offset bits, page bits, frame bits and the page table size.
A: Offset = log₂4K = 12. Page bits = 32−12 = 20 → 2²⁰ pages. Physical address = 30 bits → frame bits = 30−12 = 18. Page table = 2²⁰ × 4 B = 4 MB per process.

Multilevel paging

A 4 MB page table per process is wasteful, so we page the page table itself. With 4 KB pages and 4-byte PTEs, one page holds 4096/4 = 1024 entries = 2¹⁰. So the 20 page bits split into 10 (outer) + 10 (inner): address = [10 | 10 | 12]. Only the parts of the table actually in use need to exist. Cost: more memory accesses on a miss (2 table lookups + 1 data access for 2 levels).

TLB and effective access time

The TLB is a tiny, fast cache of recent page-table entries. Hit → skip the page table lookup.

EAT = h × (t_tlb + t_mem)  +  (1 − h) × (t_tlb + 2·t_mem)     (single-level page table)
For a k-level table, a TLB miss costs t_tlb + (k+1)·t_mem.
Worked numerical
Q: TLB access 20 ns, memory access 100 ns, TLB hit ratio 90%, single-level paging. Find EAT.
A: EAT = 0.9(20+100) + 0.1(20+200) = 108 + 22 = 130 ns.

Segmentation (quick)

Memory is divided into variable-size logical units (code, stack, heap). Address = (segment no, offset). The segment table stores base and limit; if offset ≥ limit the hardware traps. Segmentation matches how programmers think but suffers external fragmentation; paging is invisible to the programmer.

Inverted page table 🟡 Extension · rarely tested

A normal page table has one entry per virtual page of each process. An inverted page table has one entry per physical frame: each entry records (process id, page number) of the page currently in that frame, and the index of the matching entry is the frame number. Translation searches the table for (pid, page) — made fast with a hash table plus a TLB.

Worked numerical
Q: 32-bit virtual addresses, 4 KB pages, 4-byte entries, 64 MB of RAM. Compare the page-table size per process with an inverted table using 8-byte entries.
A: Normal: 2³²/2¹² = 2²⁰ pages × 4 B = 4 MB per process. Inverted: 64 MB / 4 KB = 2¹⁴ = 16384 frames × 8 B = 128 KB for the whole system, however many processes exist.

Buddy system 🟡 Extension · rarely tested

Memory is allocated in blocks whose size is a power of two. A request is rounded up to the next power of two; if no block of that size is free, a larger block is repeatedly split in half — the two halves are buddies. On release, a block is merged with its buddy if that buddy is also free, and the merge repeats upward. A block's buddy address = block address XOR block size. Merging is fast, but the rounding causes internal fragmentation (up to nearly 50%). Linux uses it for physical page frames.
Worked example
Q: From 1024 KB, allocate a 70 KB request.
A: 
1024 → split into 512 + 512      (use one 512)
 512 → split into 256 + 256
 256 → split into 128 + 128      128 ≥ 70 and 64 < 70  → allocate a 128 KB block
Free blocks left: 512 (other half), 256, 128.   Internal fragmentation = 128 − 70 = 58 KB.

6. Virtual Memory

Run programs bigger than RAM by keeping only the needed pages in memory, and the rest on disk.

Demand paging & page faults 🟢 Core

A page is loaded only when first used. If the page table says the page is not in memory (valid bit = 0), the CPU raises a page fault:

Trap to OS
→
Find page on disk
→
Get a free frame (or evict one)
→
Read page in, update table
→
Restart the instruction
EAT = (1 − p) × t_mem  +  p × t_fault        (p = page fault rate)
Worked numerical
Q: Memory access 200 ns, page fault service time 8 ms, p = 1/1000. Find EAT, then the maximum p for at most 10% slowdown.
A: t_fault = 8,000,000 ns. EAT = 0.999×200 + 0.001×8,000,000 = 199.8 + 8000 ≈ 8200 ns (a 40× slowdown!).
For ≤10% slowdown: EAT ≤ 220 → 200 + p(8,000,000 − 200) ≤ 220 → p ≤ 20 / 7,999,800 ≈ 2.5 × 10⁻⁶ (about 1 fault per 400,000 accesses). Page faults must be extremely rare.

Classic result

Thrashing 🟢 Core

If a process does not have enough frames, it faults constantly and spends more time swapping than computing. CPU utilization drops, and a naive OS may then admit more processes, making it worse. Cure: reduce the degree of multiprogramming or use the working-set model (give each process enough frames for the pages it actively uses).

Second-chance (Clock) page replacement 🔵 High-Yield · page replacement variant

FIFO with a safety valve. Frames sit in a circular list with a pointer (the clock hand); each frame has a reference bit that is set to 1 when the page is used. On a fault the hand sweeps: if the bit is 1 it is cleared to 0 and the hand moves on (a second chance); if it is 0 that page is the victim. The new page is loaded with its bit = 1 and the hand moves past it. If every bit is 1 the hand clears them all and replaces the first frame — the algorithm degenerates to FIFO.

Enhanced clock uses the pair (reference, modify): (0,0) best victim → (0,1) → (1,0) → (1,1) worst, because clean, unused pages are cheapest to evict. A full trace is in solved problem Q16.

LFU, MFU and counting-based replacement 🟡 Extension · rarely tested

LFU — least frequently usedPage with the smallest reference countActively used pages have large counts. Weakness: a page used heavily early on keeps its big count forever (fix: periodically halve the counts)
MFU — most frequently usedPage with the largest countThe page with the smallest count was probably just brought in and has not been used yet. Rare in practice

Neither is common; real systems use LRU approximations (reference bit, additional-reference-bits aging, second chance). Recall that FIFO suffers Belady's anomaly while LRU and OPT (stack algorithms) do not.

Frame allocation & global vs local replacement 🔵 High-Yield · virtual memory background

Every process needs a minimum number of frames, fixed by the instruction set (the most pages one instruction can touch, e.g. with indirect addressing).

Global replacement
The victim may be a frame of any process. Higher throughput and flexible, but a process's fault rate depends on the others, and a high-priority process can steal frames — thrashing can spread.

FAT file system 🔵 High-Yield · file-system background

The File Allocation Table sits at the start of the volume and has one entry per disk block (cluster). A directory entry stores only the first block number of a file; each FAT entry holds the next block of the chain, an end-of-file marker, or a free/bad marker. Entry widths give FAT-12, FAT-16 and FAT-32. Reaching the k-th block means following k − 1 links — cheap when the FAT is cached in memory, because no data block has to be read to find the chain. FAT size = number of blocks × entry size.
Worked numerical
Q: 512 GB disk, 4 KB blocks, 4-byte FAT entries. FAT size? How many FAT entries does a 100 KB file use?
A: Blocks = 2²⁷, so FAT = 2²⁷ × 4 B = 2²⁹ B = 512 MB. The file occupies 100/4 = 25 blocks → a chain of 25 FAT entries.

I/O subsystem: polling, interrupts and DMA 🔵 High-Yield · I/O scheduling background

TechniqueHow data moveCPU cost
Programmed I/O (polling)CPU repeatedly reads the device status register (busy-waiting), then copies each wordHighest — the CPU is tied up for the whole transfer
Interrupt-driven I/ODevice interrupts when ready; the CPU copies each byte or wordOne interrupt per byte or word
DMAA DMA controller moves a whole block between device and memory without the CPUSetup plus one interrupt per block
DMA steps: (1) the CPU programs the controller with the memory address, byte count and direction; (2) the controller requests the bus; (3) it transfers the block directly; (4) it raises one interrupt when the count reaches zero.

Modes: burst (block) mode — the controller keeps the bus for the entire block, so the CPU is locked out of memory meanwhile; cycle stealing — it takes the bus one word at a time between CPU cycles, slowing the CPU slightly; transparent mode — it transfers only when the CPU is not using the bus.
Worked numerical
Q: A 1 GHz CPU serves a device moving 100 blocks of 16 KB per second. Interrupt-driven I/O costs 300 cycles per byte; DMA costs 1500 cycles per block (setup + completion interrupt). What fraction of CPU time goes to I/O in each case?
A: Interrupt-driven: 16384 × 300 = 4,915,200 cycles per block × 100 = 4.9152 × 10⁸ cycles/s → 49.15% of the CPU. DMA: 1500 × 100 = 1.5 × 10⁵ cycles/s → 0.015%.

RAID (redundant arrays of disks) 🟡 Extension · not named in 2027

RAID combines several disks for speed (striping) and/or fault tolerance (mirroring or parity). It is a lighter GATE topic than disk scheduling, but the capacity and failure rules are quick marks.

LevelIdeaUsable capacity (N disks of size D)Failures survived
RAID 0Striping, no redundancyN × D0 — one failure loses everything
RAID 1Mirroring (every block written to two disks)N × D / 21 per mirrored pair (at least 1)
RAID 5Block striping with distributed parity (parity = XOR of the data blocks of a stripe)(N − 1) × D1

Parity recovery. If a stripe holds blocks A, B, C and parity P = A ⊕ B ⊕ C, a lost block is rebuilt by XOR-ing all the survivors: e.g. A = B ⊕ C ⊕ P.

RAID 5 small-write penalty. Updating one data block needs 4 disk I/Os: read old data, read old parity, write new data, write new parity (new P = old P ⊕ old data ⊕ new data). Because parity is distributed across all disks rather than kept on one dedicated disk (RAID 4), no single parity disk becomes the write bottleneck.
Worked numerical
Q: Six 4 TB disks are used as (a) RAID 0, (b) RAID 1, (c) RAID 5, (d) RAID 6. Find the usable capacity of each.
A: (a) 6 × 4 = 24 TB; (b) 24/2 = 12 TB; (c) (6 − 1) × 4 = 20 TB; (d) (6 − 2) × 4 = 16 TB.

Q21 · Mutual exclusion — which entry protocol is correct?
Two processes P0 and P1 (let j = 1 − i) share int flag[2] = {0,0} and int turn. Each loops forever: entry code, critical section, then the exit code flag[i] = 0. Three entry codes are proposed:
A: flag[i] = 1; turn = i; while (flag[j] && turn == i);
B: flag[i] = 1; while (flag[j]);
C: while (flag[j]); flag[i] = 1;
Which of them satisfy BOTH mutual exclusion and progress (no deadlock)?
  1. B only
  2. A and B only
  3. A only
  4. None of them
Each statement is atomic. Test every protocol by looking for (a) both processes in the CS, (b) a state from which nobody can ever enter.

C  (check, then set) :  P0 sees flag[1] = 0, is preempted; P1 sees flag[0] = 0.
                        Both then set their flags and enter  →  MUTUAL EXCLUSION VIOLATED.
B  (set, then check) :  ME holds, but P0 sets flag[0] = 1, P1 sets flag[1] = 1, and now each spins on the
                        other's flag forever  →  DEADLOCK (progress violated).
A  (turn = i, 'last writer waits'):
        the process that writes turn LAST is the one that waits (it is the one for whom turn == i), so the other
        process enters. If only one process is interested, flag[j] = 0 and it enters at once.
        This is Peterson's algorithm with the meaning of turn mirrored (turn_A = 1 − turn_Peterson):
        ME ✔, progress ✔, and bounded waiting ✔ (the other process can overtake at most once).

Check: exploring every interleaving gives 34 reachable states for A (no ME violation, none from which the CS is
unreachable), 15 for B (ME holds, 1 trapped state — the two-flags deadlock) and 16 for C (the state CS/CS is reachable).
In A, after P0 has announced itself, P1 can enter the CS at most once before P0 does.
Trap: A looks 'wrong' only because turn is set to oneself; what matters is that the LAST writer of turn is the one who waits.

Correct: Option 3 — only protocol A is correct.

Q22 · Bounded buffer — effect of swapping the semaphore order
A buffer has N = 2 slots. Semaphores: mutex = 1, empty = 2, full = 0. The Consumer is: down(full); down(mutex); remove item; up(mutex); up(empty). The Producer is written as: down(mutex); down(empty); insert item; up(mutex); up(full). Which statement is correct?
  1. There is no deadlock; the buffer never holds more than 2 items
  2. Deadlock is possible, with 1 item in the buffer
  3. Deadlock is possible, with the buffer empty
  4. Deadlock is possible, with the buffer full (2 items)
Correct producer order is down(empty) FIRST, then down(mutex). Here the order is reversed.

Interleaving that deadlocks:
  Producer inserts item 1 and item 2                →  empty = 0, full = 2, buffer FULL
  Consumer runs down(full) (full = 1) and is preempted before down(mutex)
  Producer starts item 3:  down(mutex) succeeds (mutex = 0), then down(empty) blocks because empty = 0
  Consumer resumes:        down(mutex) blocks because the producer holds it
The producer holds mutex waiting for empty; the consumer must take mutex before it can ever signal empty (up(empty)).
That is a circular wait → deadlock with 2 items in the buffer.

Check: exhaustively exploring the 32 reachable states of the swapped-order system finds exactly one deadlock state, and in it
the buffer holds 2 items (producer waiting for empty, consumer waiting for mutex).
With the correct order (down(empty), then down(mutex)) all 31 reachable states can move, there is no deadlock and the
buffer never exceeds 2 items.
Rule: always acquire the counting semaphore (resource availability) BEFORE the mutex that guards the shared structure.

Correct: Option 4 — deadlock can occur while the buffer is full.

🧭 Problem → Standard Method Playbook

Recognize the OS problem family first; then use the corresponding invariant, recurrence, graph, or accounting equation.
1. Scheduling
Build the execution timeline first. Mark arrivals and preemptions, then calculate completion time C, turnaround C−A, waiting turnaround−burst, and response first start−arrival. Add context-switch overhead only where the schedule actually switches.
2. HRRN / MLFQ
HRRN is non-preemptive: at each completion choose the arrived job maximizing (waiting+burst)/burst. MLFQ is priority-queue based: determine the queue/quantum rule, then apply demotion, promotion/aging, and preemption exactly as specified.
3. Deadlock / Banker
Separate prevention, avoidance, and detection. For Banker, compute Need = Max−Allocation, maintain Work, and repeatedly find a process whose Need ≤ Work; then release its Allocation. A complete safe sequence proves the state is safe.
4. Paging / TLB
Split address into page number + offset. Offset bits = log₂(page size). For EAT, enumerate TLB-hit and TLB-miss paths rather than memorising a formula blindly.
5. Page replacement
Maintain the frame contents after every reference. FIFO → oldest arrival; LRU → least recently referenced; OPT → page whose next use is farthest in the future; Clock → reference-bit second chance. Count faults only after checking whether the referenced page is already resident.
6. Disk scheduling
Draw the cylinder line and mark the initial head. For SCAN/C-SCAN, determine direction and whether the endpoint is physically visited under the question's convention. Total movement is the sum of absolute head-position differences.
7. File systems / links
Distinguish inode metadata, directory entries, allocation method, and free-space management. Hard links share an inode; symbolic links store a pathname and can dangle. In FAT, follow the FAT chain from the first block.
8. I/O
Polling = CPU repeatedly checks status; interrupt-driven I/O = device notifies CPU; DMA = controller transfers a block with minimal CPU intervention. Buffering handles rate mismatch; spooling queues whole jobs for a dedicated device.

🎯 Representative GATE-Style Worked Problems

HRRN
Q: At time 0, P1 arrives with burst 8. At time 2, P2 arrives with burst 4; at time 4, P3 arrives with burst 2. Which process runs after P1 under HRRN?
A: P1 finishes at t=8. Waiting: P2=6, P3=4. Ratios: P2=(6+4)/4=2.5; P3=(4+2)/2=3. Therefore P3 runs next.
MLFQ
Q: A job uses its entire quantum repeatedly while another frequently blocks for I/O. Under the standard MLFQ rule that full-quantum jobs are demoted, what happens?
A: The CPU-bound job moves to a lower-priority queue; the I/O-bound job tends to remain in a higher queue. Aging/priority boost can later prevent starvation.
Banker's algorithm
Q: A system has Available = (3,3,2). P1 Need=(1,2,2), P2 Need=(2,1,0), P3 Need=(4,0,1). Which process can safely finish first?
A: Compare Need with Available component-wise. P1 satisfies (1,2,2) ≤ (3,3,2), so P1 can finish and release its Allocation. P2 also satisfies the current Work vector. A complete safe sequence must then be constructed; one qualifying first choice alone is not sufficient to claim the entire state safe.
Paging
Q: A 32-bit address uses 4 KB pages. How many bits are the page offset?
A: 4 KB = 2¹² bytes, so the offset is 12 bits. The remaining 20 bits identify the virtual page.
LRU
Q: With 3 frames and reference string 1,2,3,1,4,2,1,3,4, how is an LRU replacement decided at the reference to 4?
A: Before 4, frames contain 1,2,3. Their most recent uses are 1 at the immediately previous reference, 2 at the earlier reference, and 3 at the initial reference. Therefore 3 is least recently used and is replaced.
Disk scheduling
Q: The disk head is at 50 and requests are 82, 170, 43, 140. Under FCFS, what total head movement occurs?
A: Movement = |50−82| + |82−170| + |170−43| + |43−140| = 32+88+127+97 = 344 cylinders.
