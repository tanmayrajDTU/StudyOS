1. Principles of Layering

Why real networks are built as a stack of independent layers, and how data gets wrapped and unwrapped as it travels through them.

Why layer at all? 🟢 Core

A network has to solve many different problems at once: turning bits into electrical signals, getting a frame across one wire, routing across the globe, making delivery reliable, and letting an app request a web page. Layering splits this into independent jobs — each layer offers a clean service to the layer above and uses services from the layer below, without needing to know how those services are implemented internally.

The classic 7-layer OSI model (with separate Session and Presentation layers) is still useful background, but the current syllabus focuses on the practical TCP/IP 5-layer model actually used on the real internet. Know that OSI's Session+Presentation+Application roughly collapse into TCP/IP's single Application layer.

Encapsulation & decapsulation 🟢 Core

As data goes DOWN the stack at the sender, each layer wraps the data from above inside its own header (and sometimes trailer) — this is encapsulation. At the receiver, data goes UP the stack and each layer strips off its own header — decapsulation.

App data
  → [TCP header | App data]                      = Segment
    → [IP header | TCP header | App data]         = Packet
      → [Ethernet header | IP header | ... | Ethernet trailer] = Frame
        → 1011010010110...                        = Bits on the wire
Each layer only reads/writes its OWN header — it treats everything from the layer above as opaque data (this is exactly what "layering" buys you: a router only looks at the IP header, never at the TCP or application data inside).
Worked numerical
Q: An application sends 1000 bytes of data. TCP adds a 20-byte header, IP adds a 20-byte header, and Ethernet adds an 18-byte header+trailer. What is the total frame size placed on the wire, and what is the header overhead as a percentage?
A: Total = 1000 + 20 + 20 + 18 = 1058 bytes. Overhead = 58 bytes → 58/1058 ≈ 5.5% of the frame is pure header/trailer overhead.

2. Switching & Performance Metrics

How data actually moves through the network's internal switches/routers, and the formulas GATE uses to measure "how fast".

Three switching techniques 🟢 Core

TypeHow it worksProsCons
Circuit switchingA dedicated end-to-end path is reserved before data flows (e.g. old telephone network)Guaranteed bandwidth, predictable delay once set upSetup/teardown time; wastes capacity if the link sits idle
Packet switchingData is split into packets, each routed independently ("store-and-forward"), no reservationEfficient — links shared via statistical multiplexingVariable, unpredictable delay (congestion, queuing)
Virtual circuit switchingA logical path is set up once (like circuit switching), but data still travels as separate packets along itCombines fast, ordered forwarding with statistical sharingStill needs setup signaling; used in ATM, MPLS, Frame Relay

Delay components — memorize these four 🟢 Core · performance metrics

Transmission delay = L / B      (L = packet size in bits, B = link bandwidth in bits/sec)
Propagation delay  = d / v      (d = distance, v = signal propagation speed in the medium)
Queuing delay       = time waiting in a router's buffer before transmission
Processing delay    = time a router/switch takes to examine the packet header
Total end-to-end delay for ONE hop = Transmission + Propagation + Queuing + Processing.
Worked numerical
Q: A 10 Mbps link carries a 5000-bit packet over a 2000 km cable where the signal travels at 2×10⁸ m/s. Find the transmission delay, propagation delay, and total delay (ignore queuing/processing).
A: 
Transmission delay = 5000 bits / (10×10⁶ bps) = 0.5 ms
Propagation delay  = (2000×1000 m) / (2×10⁸ m/s) = 10 ms
Total delay = 0.5 + 10 = 10.5 ms
Notice propagation dominates over long distances even at decent bandwidth — a classic GATE observation.

Store-and-forward delay across multiple hops (packet switching) 🟢 Core · performance metrics

In pure packet switching, a router must receive the entire packet before it can start forwarding it to the next hop (it can't forward partial packets).

Worked numerical
Q: A packet of L=6400 bits travels through 3 links (2 intermediate routers) to reach its destination, each link having bandwidth B=1 Mbps. Ignoring propagation delay, find the total time for the packet to reach the destination.
A: Each hop needs a full transmission time of L/B = 6400/(1×10⁶) = 6.4 ms before the NEXT hop can even begin (store-and-forward). 
Total time (ignoring propagation) = number_of_links × (L/B) = 3 × 6.4 ms = 19.2 ms
General formula: for n links (n−1 intermediate routers), Total ≈ n × (L/B) + Σ(propagation delays).
Worked numerical — circuit switching comparison
Q: The same data (6400 bits) is sent using circuit switching over the same 3-link path (B=1 Mbps per link), with a call setup time of 15 ms and negligible propagation delay. Compare total time to the packet-switched case above.
A: Once the circuit is set up, data flows straight through at the bottleneck rate without per-hop store-and-forward waiting: 
Circuit switching total = setup time + transmission time = 15 + 6.4 = 21.4 ms
Packet switching total (from above) = 19.2 ms
Here packet switching is actually faster for a single message, because circuit switching pays a big upfront setup cost — this trade-off (setup overhead vs. per-hop store-and-forward overhead) is exactly what GATE likes to compare.

Bandwidth-Delay Product 🟢 Core · performance metrics

Bandwidth-Delay Product (BDP) = Bandwidth × RTT
This is the amount of data that can be "in flight" on the link at any instant — the size of the "pipe". It tells you the minimum window size (Part 3) needed to keep a link 100% utilized.
Worked numerical
Q: A link has bandwidth 100 Mbps and RTT 40 ms. Find the bandwidth-delay product, and the minimum window size (in bytes) needed to keep the link fully utilized.
A: 
BDP = 100×10⁶ bps × 40×10⁻³ s = 4×10⁶ bits = 4,000,000 bits
    = 4,000,000 / 8 = 500,000 bytes = 500 KB
The sender needs a window of at least 500 KB "in flight" at all times, or the link will sit idle waiting for acknowledgments — this is exactly why TCP's window size matters so much on high-bandwidth, high-latency ("long fat") links.

Worked numerical
Q: A T1 line multiplexes 24 voice channels of 64 kbps. What is its line rate?
A: Each frame carries 24 × 8 = 192 data bits plus 1 framing bit = 193 bits, sent 8000 times per second: 193 × 8000 = 1.544 Mbps. The payload alone is 24 × 64 kbps = 1.536 Mbps; the extra 8 kbps is framing overhead.

3. Data Link Layer & MAC

Getting a frame across ONE link correctly, deciding who gets to talk when many devices share the medium — including sliding-window flow control, Hamming codes and channel capacity.

Q: Data = 1101011011, Generator = 10011 (a 4-bit CRC, so append 4 zeros). Find the CRC remainder and the transmitted frame.
A: 
Message with 4 zeros appended: 11010110110000  (14 bits)

whenever the leading bit of the current window is 1, otherwise just shift:

  10011                    →

  01001

(GATE typically gives you the full division to perform by hand — practice mod-2 long division carefully, it's just repeated XOR, no carries.)

Q: Bit-stuff the data 0111110111111011111. Byte-stuff the data 7E 41 7D 42 (FLAG = 7E, ESC = 7D).

Medium Access Control (MAC) — who transmits when? 🟢 Core

ALOHA

Pure ALOHA
Transmit whenever you have data — no coordination at all. Throughput: S = G·e^(-2G). Maximum at G=0.5: S_max ≈ 18.4%.
Slotted ALOHA
Time is divided into slots; transmit only at slot boundaries. Throughput: S = G·e^(-G). Maximum at G=1: S_max ≈ 36.8%.
Worked numerical
Q: In a slotted ALOHA system, the offered load G = 2. Find the throughput S.
A: S = G·e^(-G) = 2·e^(-2) = 2 × 0.1353 ≈ 0.271 (27.1% — notice this is LOWER than the peak at G=1, since too many stations are now colliding).

CSMA / CSMA-CD / CSMA-CA

ProtocolRuleUsed in
CSMA (Carrier Sense)Listen before transmitting ("listen before talk")Basic wired LANs
CSMA/CDListen while transmitting; if a collision is detected, abort immediately and back offClassic (wired) Ethernet
CSMA/CACan't reliably detect collisions (wireless), so try to AVOID them — random backoff before every transmission, optional RTS/CTS handshakeWi-Fi (802.11)
Why CSMA/CD needs a MINIMUM frame size
A transmitting station must still be sending when a collision's signal comes back, or it will never know the collision happened. This forces: Transmission time ≥ 2 × Propagation time.
Worked numerical — minimum Ethernet frame size
Q: A CSMA/CD LAN has bandwidth 10 Mbps, and the maximum distance between two stations is 2500 m, with signal speed 2×10⁸ m/s. Find the minimum frame size needed.
A: 
Propagation delay (one way) = 2500 / (2×10⁸) = 12.5 μs
Worst case: collision signal must travel there AND back → 2 × Tprop = 25 μs

Minimum transmission time = 2 × Tprop = 25 μs
Minimum frame size = Bandwidth × Minimum transmission time
                    = 10×10⁶ bps × 25×10⁻⁶ s = 250 bits ≈ 32 bytes
(Real Ethernet uses extra safety margin, giving the well-known 64-byte minimum frame size — but the derivation logic is exactly this "2 × Tprop" rule.)

Ethernet framing & addressing 🟢 Core

Each device has a globally unique 48-bit MAC address burned into its NIC. A switch forwards frames only out the port leading to the destination MAC (learned by watching source addresses), unlike a hub which blindly repeats to every port — this is why switches eliminate collisions entirely (each switch port is its own collision domain).

Flow control at the link layer — sliding window protocols 🔵 High-Yield · foundation for TCP flow control

Let Tt = frame transmission time (L/B) and Tp = propagation delay, and define a = Tp / Tt. A sender that waits for each ACK idles for a whole round trip (2Tp), so keeping the link busy needs several frames in flight.

ProtocolSender / receiver windowEfficiency (utilisation)Sequence numbers (k bits)After a lost frame
Stop-and-wait1 / 11 / (1 + 2a)1 bit (0, 1)Resend that frame after the timeout
Go-Back-NN / 1N / (1 + 2a), capped at 1N ≤ 2k − 1Resend the lost frame and every later one; receiver discards out-of-order frames
Selective RepeatN / NN / (1 + 2a), capped at 1N ≤ 2k−1 (sequence space ≥ 2N)Resend only the lost frame; receiver buffers out-of-order frames
The window that keeps the pipe exactly full is 1 + 2a frames. Efficiency can never exceed 1, so for N ≥ 1 + 2a the utilisation is 100%. If a question gives the round-trip time directly: efficiency = N·Tt / (Tt + RTT). ACK transmission time is ignored unless the question says otherwise.
Worked numerical
Q: A 1 Mbps link, 200 km long (signal speed 2×10⁸ m/s), carries 1000-bit frames. Find the stop-and-wait efficiency and throughput, the window needed for full utilisation, and the sequence-number bits needed for Go-Back-N and for Selective Repeat at that window.
A: Tt = 1000 / 10⁶ = 1 ms; Tp = 200 000 / (2×10⁸) = 1 ms, so a = 1. 
Stop-and-wait: η = 1/(1+2a) = 1/3 = 33.3%  →  throughput = 1 Mbps × 1/3 ≈ 333 kbps
Window for 100% = 1 + 2a = 3 frames
Go-Back-N : N + 1 = 4 sequence numbers  →  2 bits
Selective Repeat: 2N = 6 sequence numbers → 3 bits
Worked numerical
Q: Tt = 1 ms and Tp = 5 ms. What is the efficiency of Go-Back-N with N = 7?
A: a = 5, so 1 + 2a = 11. Efficiency = 7 / 11 ≈ 63.6%. With N = 11 or more it would reach 100%.
GATE trap
With 3-bit sequence numbers Go-Back-N can use a window of 7, but Selective Repeat only 4. If the Selective Repeat window equals the whole sequence space, a retransmitted old frame cannot be told apart from a new one.

Error correction — Hamming code 🟡 Extension · not in the 2027 list

For m data bits, r check bits are needed so that 2r ≥ m + r + 1: m = 4 → r = 3 (the (7,4) code); m = 7 or 8 → r = 4. Check bits sit at the power-of-two positions 1, 2, 4, 8, … and each one gives even parity over the positions whose binary index contains that bit. After a single-bit error, the syndrome (the failing checks read as a binary number) equals the position of the flipped bit. In terms of minimum Hamming distance d: a code detects up to d − 1 errors and corrects up to ⌊(d − 1)/2⌋ (the (7,4) code has d = 3).

Worked numerical
Q: Encode data bits 1 0 1 1 with the (7,4) Hamming code (even parity), then locate the error if the received word is 0110111.
A: Positions 1…7 are p1 p2 d3 p4 d5 d6 d7, with d3 d5 d6 d7 = 1 0 1 1. 
p1 covers 1,3,5,7: 1⊕0⊕1 = 0      p2 covers 2,3,6,7: 1⊕1⊕1 = 1      p4 covers 4,5,6,7: 0⊕1⊕1 = 0
Codeword = 0 1 1 0 0 1 1  (0110011)
Received 0110111: checks p1 → 1 (fails), p2 → 0 (ok), p4 → 1 (fails)
Syndrome = (p4 p2 p1) = 101 = 5  →  bit 5 flipped; correct it to get 0110011.

Channel capacity and line coding 🟡 Extension · not in the 2027 list

LawFormulaUse when
NyquistC = 2 B log₂ L bpsNoiseless channel, L signal levels, bandwidth B Hz
ShannonC = B log₂(1 + S/N) bpsNoisy channel; this is the upper limit whatever the signal levels

Convert decibels first: S/N = 10(SNRdB/10), so 30 dB means S/N = 1000. When a problem gives both limits, the achievable rate is the smaller of the two.

Worked numerical
Q: A 3 kHz telephone line has a 30 dB signal-to-noise ratio. What is its maximum data rate? What does Nyquist give for a noiseless 4 kHz channel with 8 levels?
A: S/N = 10³ = 1000, so Shannon: C = 3000 × log₂(1001) ≈ 3000 × 9.97 ≈ 29.9 kbps. Nyquist: C = 2 × 4000 × log₂ 8 = 2 × 4000 × 3 = 24 kbps.
Line coding. Manchester encoding puts a transition in the middle of every bit and the direction of that transition carries the bit value (textbooks differ on which direction means 1, so follow the convention the question states), so the receiver can recover the clock, but the signalling rate is twice the bit rate — 10 Mbps Ethernet used a 20 Mbaud signal. NRZ uses one signal level per bit (baud rate = bit rate) but long runs of equal bits lose synchronisation.

4. Routing Algorithms

How routers figure out the best path across a whole network of routers, without any single router knowing the entire map upfront (in the distance-vector case).

Modeling the network as a graph 🟢 Core · supports DV / LS

Routers = nodes, links = edges, link costs = edge weights (could be based on delay, hop count, or bandwidth). Both algorithms below try to find the shortest-cost path from every router to every other router.

Distance Vector Routing (Bellman-Ford based) 🟢 Core

Each router only knows the cost to its direct neighbors. It periodically shares its entire distance table with its neighbors, and each router updates its own table using the Bellman-Ford equation:

D_x(y) = min over all neighbors v of { c(x,v) + D_v(y) }
"My best cost to Y = my link cost to neighbor V, plus V's own best-known cost to Y — minimized over every neighbor V."
Worked numerical
Q: 3 routers A, B, C. Direct link costs: A-B=2, B-C=1, A-C=7. Using distance vector routing, what does A's table converge to for reaching C?
A: 
Initial: A's table — A-B=2, A-C=7 (direct link only)
B shares its table with A: B says "my cost to C = 1"
A recomputes: D_A(C) = min( c(A,C)=7 ,  c(A,B)+D_B(C) = 2+1=3 ) = min(7,3) = 3

A updates its table: cost to C via B = 3 (better than the direct 7-cost link)
Next hop for C, from A's table: via B
This is exactly how distance vector routing "discovers" that going through B is cheaper than A's own direct link to C — information propagates hop by hop until everyone converges.
Count-to-infinity problem
If a link fails, bad news (increased cost) travels much slower than good news, because routers can keep telling each other stale, now-wrong "shortcuts" back and forth, incrementing the cost by tiny amounts each round instead of realizing the path is broken. Fixes: split horizon (don't advertise a route back to the neighbor you learned it from) and poison reverse.

Link State Routing (Dijkstra based) 🟢 Core

Every router floods its direct link costs to the ENTIRE network (not just neighbors), so every router ends up with a full map of the topology. Each router then independently runs Dijkstra's algorithm on this map to compute shortest paths to everyone.

Worked numerical — Dijkstra's trace
Q: Graph: A-B=4, A-C=1, C-B=2, C-D=5, B-D=1. Find shortest paths from A to every other node.
A: 
Initialize: dist[A]=0, dist[B]=∞, dist[C]=∞, dist[D]=∞.  Visited={}

Round 1: pick unvisited min-dist node = A (dist 0). Visit A.
  Update neighbors: dist[B]=min(∞,0+4)=4,  dist[C]=min(∞,0+1)=1

Round 2: pick unvisited min-dist = C (dist 1). Visit C.
  Update neighbors: dist[B]=min(4, 1+2=3)=3 (better via C!)
                    dist[D]=min(∞, 1+5=6)=6

Round 3: pick unvisited min-dist = B (dist 3). Visit B.
  Update neighbors: dist[D]=min(6, 3+1=4)=4 (better via B!)

Round 4: pick unvisited min-dist = D (dist 4). Visit D. Done.

Final shortest distances from A:  B=3 (path A-C-B),  C=1 (direct),  D=4 (path A-C-B-D)

5. IPv4: Fragmentation, CIDR & NAT

How a single IP datagram survives crossing links with different maximum sizes, how addresses are carved up efficiently, and how millions of devices share one public IP.

Fragmentation 🟢 Core

Every link has a Maximum Transmission Unit (MTU) — the largest frame it can carry. If a datagram is bigger than the next link's MTU, a router splits it into fragments. Each fragment gets its own IP header, with three key fields: Identification (same for all fragments of one datagram), Fragment Offset (position of this fragment's data, in units of 8 bytes), and the MF (More Fragments) flag (1 for all fragments except the last).

Worked numerical
Q: A 4000-byte IP datagram (20-byte header + 3980-byte data) must cross a link with MTU = 1500 bytes. How many fragments are needed, and what is each fragment's offset?
A: 
Data per fragment (excluding the 20-byte header each fragment needs) must be
a multiple of 8 bytes, and at most 1500-20=1480 bytes → use 1480 bytes/fragment.

Total data to carry = 3980 bytes
Fragment 1: data bytes 0-1479    (1480 bytes) → offset = 0/8 = 0,      MF=1
Fragment 2: data bytes 1480-2959 (1480 bytes) → offset = 1480/8 = 185, MF=1
Fragment 3: data bytes 2960-3979 (1020 bytes) → offset = 2960/8 = 370, MF=0 (last)

Total fragments = 3
Each fragment is now (20-byte header + its data) ≤ 1500 bytes, satisfying the MTU.

CIDR (Classless Inter-Domain Routing) 🟢 Core

Instead of rigid class A/B/C blocks, CIDR writes an address as a.b.c.d/n, where n is the number of leading bits that form the network portion (the "subnet mask" length).

Number of host addresses in a /n block = 2^(32-n)
Usable hosts (excluding network & broadcast addresses) = 2^(32-n) - 2
Worked numerical
Q: Given the block 192.168.10.0/26, find the network address, broadcast address, and number of usable hosts.
A: 
/26 means 26 network bits, 32-26 = 6 host bits → 2^6 = 64 total addresses
Network address = 192.168.10.0     (all host bits = 0)
Broadcast address = 192.168.10.63  (all host bits = 1, since 64-1=63)
Usable hosts = 64 - 2 = 62
Worked numerical — subnetting
Q: You are given 192.168.1.0/24 and must split it into 4 equal-sized subnets. Find each subnet's CIDR block.
A: 
4 subnets needs 2 extra bits (2² = 4) → new prefix = /24+2 = /26 (64 addresses each)
Subnet 1: 192.168.1.0/26     (.0  to  .63)
Subnet 2: 192.168.1.64/26    (.64 to  .127)
Subnet 3: 192.168.1.128/26   (.128 to .191)
Subnet 4: 192.168.1.192/26   (.192 to .255)

NAT (Network Address Translation) 🟢 Core

Private networks use reserved address ranges (like 192.168.0.0/16, 10.0.0.0/8) that are never routed on the public internet. A NAT router at the network's edge rewrites the (private IP, private port) of outgoing packets to a single (public IP, chosen port), keeping a translation table so replies can be routed back correctly.

Two internal hosts using the SAME private port (5000) are distinguished on the public side purely by the different port NAT assigns them (40001 vs 40002) — this is exactly why NAT lets one public IP serve an entire private network.

IP support protocols — ARP, DHCP, ICMP 🟡 Extension · not in the 2027 list

ARP (Address Resolution Protocol)

Maps a next-hop IP address → MAC address on the same LAN. The sender broadcasts an ARP request (destination MAC FF:FF:FF:FF:FF:FF: "who has IP x?"); the owner replies by unicast. Answers are kept in an ARP cache.

GATE classic
Going from host H1 to a host on another network, H1 ARPs for the default router's interface, not for the final destination. As a packet crosses each router the MAC addresses change at every hop, but the source/destination IP addresses stay the same (unless NAT rewrites them).

DHCP (Dynamic Host Configuration Protocol)

Gives a booting host its IP address, subnet mask, default gateway and DNS server, as a time-limited lease. Runs over UDP (server port 67, client port 68). The four steps — DORA: 
1. DISCOVER  client → broadcast (src 0.0.0.0, dst 255.255.255.255)
2. OFFER     server → proposes an address
3. REQUEST   client → broadcast, accepting one offer
4. ACK       server → confirms the lease
A relay agent forwards broadcasts to a DHCP server on another network.

ICMP (Internet Control Message Protocol)

Carried inside IP datagrams (protocol number 1); reports errors and supports diagnostics: Echo request/reply (ping), Destination unreachable, Time exceeded (TTL reached 0), Redirect. traceroute sends probes with TTL = 1, 2, 3 … ; each router that drops one returns "Time exceeded", revealing the path hop by hop. ICMP never generates errors about ICMP error messages.

128-bit addresses written as 8 groups of 4 hex digits; leading zeros may be dropped and one run of all-zero groups may be replaced by :: (2001:0db8:0000:0000:0000:ff00:0042:8329 → 2001:db8::ff00:42:8329). 6. TCP: Flow & Congestion Control

How TCP avoids overwhelming a slow receiver (flow control) and a congested network (congestion control) — and the API used to actually open a connection.

Flow control — sliding window 🟢 Core

The receiver advertises a receive window (rwnd): how many unacknowledged bytes it can currently buffer. The sender must never have more than min(cwnd, rwnd) bytes "in flight" (sent but not yet acknowledged).

Worked numerical
Q: Sender's window size is 4000 bytes, MSS (max segment size) is 1000 bytes, RTT is 100 ms. What is the maximum achievable throughput?
A: The sender can have 4000 bytes in flight per RTT (send, wait for ack, then send more): Throughput = Window size / RTT = 4000 bytes / 0.1 s = 40,000 bytes/s = 320 kbps.

Congestion control — slow start & AIMD 🟢 Core

Slow Start
cwnd starts at 1 MSS and doubles every RTT (exponential growth) until it hits ssthresh, or a loss occurs.
Congestion Avoidance (AIMD)
Once past ssthresh, cwnd grows by just +1 MSS per RTT (linear, additive increase). On a loss, ssthresh = cwnd/2 and cwnd drops (multiplicative decrease).
Worked numerical — cwnd trace
Q: ssthresh = 16 MSS. Starting from cwnd=1 MSS, trace cwnd for the first several RTTs assuming no losses.
A: 
Slow start (doubles each RTT, until reaching ssthresh=16):
RTT1: 1   RTT2: 2   RTT3: 4   RTT4: 8   RTT5: 16  (= ssthresh, switch phase here)

Congestion avoidance (adds +1 MSS each RTT from here on):
RTT6: 17   RTT7: 18   RTT8: 19 ...
If a timeout (loss) occurred at, say, cwnd=19: new ssthresh = 19/2 ≈ 9, and cwnd resets to 1, restarting slow start up to the new ssthresh=9 before switching back to linear growth.

Sequence & acknowledgment numbers, connection setup and teardown 🔵 High-Yield · background to flow / congestion control

Sequence number = byte-stream number of the first data byte in the segment. ACK number = the next byte expected (cumulative). SYN and FIN each consume one sequence number; a pure ACK consumes none. 
Setup (3-way):   Client → SYN, seq = x
                 Server → SYN+ACK, seq = y, ack = x + 1
                 Client → ACK, seq = x + 1, ack = y + 1       (data may ride with this segment)
Teardown (4-way): FIN → ACK → FIN → ACK  (each direction is closed separately — "half-close")
The side that closes first enters TIME_WAIT for 2 × MSL before releasing the connection.
Remember
Dropped, reordered or lost data makes the receiver repeat the same ACK number (duplicate ACK). Three duplicate ACKs trigger fast retransmit of the missing segment without waiting for the timer. Tahoe then restarts at cwnd = 1; Reno (fast recovery) sets ssthresh = cwnd/2 and cwnd = ssthresh (+3). A timeout always drops cwnd to 1 MSS.

RTT estimation and the retransmission timeout 🔵 High-Yield · background to congestion control

SRTT   = (1 − α)·SRTT   + α·SampleRTT          α = 1/8
RTTVAR = (1 − β)·RTTVAR + β·|SRTT − SampleRTT|   β = 1/4   (computed with the OLD SRTT, as in RFC 6298)
RTO    = SRTT + 4·RTTVAR
Karn's algorithm: never take an RTT sample from a retransmitted segment (the ACK is ambiguous), and double the RTO on every timeout (exponential back-off).

Small segments: Nagle, silly window syndrome, delayed ACK 🟡 Extension · not in the 2027 list

The problem: sending 1 byte of data costs 20 + 20 header bytes, so only 1/41 ≈ 2.4% of the packet is useful.

Nagle's algorithm (sender): send a small segment immediately only if there is no unacknowledged data in flight; otherwise buffer small writes until an ACK arrives or a full MSS has accumulated.
Silly window syndrome (receiver): a slow application reads a few bytes at a time and the receiver keeps advertising tiny windows. Clark's fix: do not advertise a new window until it can hold a full MSS (or half the buffer).
Delayed ACK: the receiver waits (at most about 500 ms) hoping to piggyback the ACK on data, and ACKs at least every second full-sized segment.

Window limits and window scaling 🟢 Core · flow control

The TCP window field is 16 bits, so the largest window is 65,535 bytes. At RTT = 100 ms this caps throughput at 65 535 × 8 / 0.1 ≈ 5.24 Mbps however fast the link is. The window-scale option (negotiated in the SYN, shift up to 14) multiplies the window by 2shift, giving up to 65 535 × 2¹⁴ ≈ 1 GB. This is the bandwidth-delay product again: the window must be at least BDP = bandwidth × RTT to keep the pipe full.

8. Problem → Standard Method Playbook

Recognize the networking problem first. Then use the standard invariant, formula, or protocol rule instead of memorizing isolated answers.

Framing / bit stuffing

Bit stuffing: after five consecutive 1s in the data, insert a 0.
At the receiver, remove the stuffed 0 after five 1s.
Byte stuffing: reserve an ESC byte and escape occurrences of the delimiter/ESC inside payload.

Trap: bit stuffing is bit-oriented; byte stuffing is byte/character-oriented.

IP fragmentation / CIDR

Prefix /p → host bits = 32−p.
Addresses in block = 2^(32−p).
First address = network; last = broadcast (IPv4 subnet).
For fragmentation, fragment payload sizes must respect the outgoing MTU and, except the final fragment, be multiples of 8 bytes. MF=1 means more fragments follow.

Routing: DV vs LS

Distance Vector → Bellman-Ford recurrence:
D_x(y) = min_v { c(x,v) + D_v(y) }
Link State → build a complete topology view, then run Dijkstra from the source.
RIP → distance-vector, hop count metric, max usable hop count 15.
OSPF → link-state, Dijkstra, cost metric.
BGP → inter-domain path-vector protocol.

TCP sequence / ACK

TCP sequence number identifies the first byte in a segment's payload.
ACK number = next byte expected (cumulative ACK).
SYN and FIN each consume one sequence number even though they carry no application data.
If segment starts at seq S and carries L bytes, next expected byte is S+L.

TCP timeout / RTO

Smoothed RTT: SRTT = (1−α)SRTT + α·SampleRTT.
RTT variation: RTTVAR = (1−β)RTTVAR + β|SRTT−SampleRTT|.
Typical RTO form: SRTT + 4·RTTVAR.
Do not use a retransmitted sample as an ordinary RTT sample (Karn's rule).

DNS / HTTP timing

DNS maps names to records; ordinary DNS queries commonly use UDP 53, while TCP 53 is used when required (e.g. zone transfer).
HTTP is application-layer request/response.
For timing questions, count each required RTT separately and add transmission/processing time only when the question gives it.
Persistent connections avoid repeated TCP handshakes; pipelining can overlap requests.

Delay / throughput

Transmission = packet bits / link rate.
Propagation = distance / propagation speed.
Store-and-forward across H links: H·(transmission + propagation) when all links have the same values and processing/queueing are ignored.
BDP = bandwidth × RTT.

GATE-Level Worked Problems

1. Bit stuffing

Suppose the payload contains 1111101. What bit-oriented stuffing occurs?

After the first five consecutive 1s, the sender inserts a 0: 11111001. The receiver removes that inserted 0 after detecting five consecutive 1s.

Trap: the inserted 0 is not application data.

2. CIDR block size

How many IPv4 addresses are in 192.168.10.0/26?

Host bits = 32−26 = 6. Therefore addresses = 2⁶ = 64. The block spans 192.168.10.0 through 192.168.10.63; in the usual subnet interpretation, .0 is the network address and .63 the broadcast address.

3. TCP sequence and ACK

A TCP segment has sequence number 1000 and carries 500 bytes of data. What cumulative ACK should the receiver send if all bytes through the segment arrived correctly?

The bytes are 1000 through 1499, so the next expected byte is 1500. ACK = 1500.

If the segment instead had SYN set and carried no data, the SYN would still consume one sequence number.

4. RTT/RTO update

Let previous SRTT = 100 ms, α = 0.125, and a new SampleRTT = 140 ms. Compute the new SRTT.

SRTT = 0.875×100 + 0.125×140 = 87.5 + 17.5 = 105 ms. In a full RTO calculation, RTTVAR must also be maintained; do not replace RTO with SRTT alone.

5. HTTP persistent timing

A page and 3 embedded objects are on the same server. RTT = R and transmission time is negligible. Under persistent HTTP with pipelining, after the TCP connection is established, requests can be sent together.

Using the standard simplified GATE model: TCP handshake = R, base-object request/response = R, pipelined embedded-object requests/responses = R. Total ≈ 3R.

Trap: if the problem explicitly includes DNS lookup or TLS handshake, add those RTTs according to the stated model.

6. Distance Vector update

Router X has neighbor A with link cost 2. A advertises distance 5 to destination Y. What candidate distance does X obtain through A?

Bellman-Ford candidate = c(X,A) + D_A(Y) = 2 + 5 = 7. X compares this with all other neighbors and chooses the minimum candidate.

Q20 · Token bucket — maximum burst and total transfer time

  1. 2 s, 20 MB, 7 s
  2. 2 s, 16 MB, 5 s
  3. 1.6 s, 16 MB, 6 s
  4. 2 s, 20 MB, 10 s
Token bucket: one token = permission to send one byte (or MB). The bucket stays full up to its capacity C, tokens arrive at rate ρ, and sending at line rate M drains it at M, while it still refills at ρ.

Net drain rate during the burst = M − ρ = 10 − 2 = 8 MB/s.
Burst length S = C / (M − ρ) = 16 / 8 = 2 s.
Data sent in the burst = M × S = 10 × 2 = 20 MB   (the 16 MB stored tokens + 4 MB of tokens that arrive meanwhile = 20 MB ✔).

After the burst the bucket is empty, so the source can only send as fast as tokens arrive: ρ = 2 MB/s.
Remaining data = 30 − 20 = 10 MB  →  10 / 2 = 5 s.
Total time = 2 + 5 = 7 s.

Leaky bucket for contrast: it smooths ANY burst to a constant rate ρ (30 MB would take 15 s); the token bucket allows bursts up to C and so keeps the average rate ≤ ρ over the long run.
Check: a millisecond-step simulation of the bucket produced a 2.000 s burst sending 20 MB.
Trap: the burst is C/(M − ρ), not C/M (that would ignore the tokens arriving during the burst); and the data sent is M·S, not just C.

Correct: Option 1 — a 2 s burst sending 20 MB, and 7 s for the 30 MB transfer.
